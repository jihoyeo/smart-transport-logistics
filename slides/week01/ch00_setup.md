# 교재 0.1–0.2 설치와 데이터

  - pip install -r requirements.txt
  - 버전 고정 — 같은 버전이면 교재와 같은 그림

> 설치 명령은 교재 0.1을 화면에 표시하고 한 줄씩 함께 실행합니다. 오류가 발생하면 명령과 오류 메시지를 확인하고, 먼저 설치를 마친 학생은 주변 학생의 진행을 도와주도록 안내합니다.

## 실습 대상: 하남시

- 선정 이유: 서울과 인접하고 노트북에서 처리할 수 있는 규모
- 저장소에 포함된 데이터
  - 도로망 노드·엣지 (parquet)
  - 통행 수요 (demand.csv)
- load_road_graph("hanam", modes=("drive",)) → 노드 12,566 · 엣지 28,589
- 노드 기준: 교차로와 막다른 길
  - 두 노드 사이의 직선 구간은 엣지 하나로 표현

> 하남시 전체 도로망인데도 노드 수가 적어 보이는 이유를 설명합니다. 도로가 꺾이는 지점까지 모두 노드로 두지 않고, 교차로와 막다른 길만 노드로 사용하기 때문입니다. modes 인자는 2장에서 자세히 다룹니다.

# 교재 0.3 엔진 연결

## DTUMOS 연결 방법

표: DTUMOS 엔진에 연결하는 세 가지 방법과 설정
| 방법 | 쓰는 상황 | 설정 |
|---|---|---|
| 공용 서버 | 수업 중 무거운 실행 | SMARTMOB_DTUMOS_URL |
| 로컬 Docker | 엔진 코드를 직접 확인할 때 | docker compose up -d |
| 녹화본 | 서버 없이 복습 | SMARTMOB_OFFLINE=1 |

- DTUMOS 엔진: Rust로 구현 · Docker로 실행 · HTTP로 요청
- 학습 범위: 엔진 내부 구현이 아닌 호출과 결과 해석
- 녹화본: 서버에 연결하지 못해도 실습 계속 진행

> 공용 서버 주소와 팀별 포트는 단톡방으로 안내합니다. 서버에 연결할 수 없으면 저장소의 data/fixtures/에 보관된 실제 실행 결과를 대신 반환합니다.

## 녹화본의 범위

- dt.health()가 반환하는 status
  - fixture — 녹화본 사용 중
  - 그 외 — 실서버 응답
- 녹화 범위: 교재에 나오는 요청만
- 차량 80대 → 81대로 변경 시 FixtureMissing
- FixtureMissing의 의미: 코드 오류가 아니라 실서버가 필요한 요청

> 학생들이 FixtureMissing을 코드 오류로 오해하지 않도록 녹화본의 범위를 설명합니다. 교재에 없는 조건으로 실행하려면 실제 서버에 연결해야 합니다.

# 교재 0.4 첫 시뮬레이션

## 첫 시뮬레이션의 실행 조건

표: 첫 시뮬레이션의 실행 조건
| 인자 | 값 |
|---|---|
| 도시 · 수단 | 하남 · 택시 |
| 차량 대수 | 80대 |
| 호출 건수 | 1,000건 |
| 시간 범위 | 1080 ~ 1440 (18:00~24:00) |

- 시간 단위: 자정부터의 분 — 책 전체 공통
- random_seed=42 고정 → 같은 결과 재현

> 각 인자와 값을 교재의 실행 코드에서 확인합니다. 시간을 자정부터 지난 분을 나타내는 정수로 표현하는 규칙은 11장의 시뮬레이션 루프에서도 그대로 사용합니다.

## 첫 실행의 결과 지표

표: sim.summary()가 반환하는 세 지표
| 지표 | 값 | 뜻 |
|---|---|---|
| service_rate | 1.0 | 호출 990건 전부 배차 |
| avg_waiting_time_min | 약 4.1분 | 호출부터 승차까지 평균 |
| utilization | 약 0.27 | 승객 탑승 시간 비율 |

- 승객 관점: 평균 대기시간 약 4.1분
- 운영 관점: 차량 가동률 약 27%
- 비교할 대안: 차량 40대일 때의 대기시간과 서비스율

> 평균 대기시간은 짧지만 차량 가동률은 27%입니다. 같은 수요와 도로망에서 차량을 40대로 줄였을 때 대기시간과 서비스율이 어떻게 달라지는지 비교할 필요가 있습니다. 이 비교에 필요한 시뮬레이터를 이후 장에서 단계별로 구현합니다.

# 교재 0.5 시간에 따른 기록

## 분 단위 기록 읽기

![하남시 18:00–24:00 시뮬레이션의 분 단위 차량·승객 기록](figures/ch00_record.png)

- sim.record: 1분당 한 행
- 운행 중 차량 증가 ↔ 대기 차량 감소
- 운행 중 차량과 대기 차량의 합: 대부분 80대

> plot_record(sim.record)로 만든 그림입니다. 설명하기 전에 학생들에게 마지막 30분의 변화를 먼저 찾아보도록 요청합니다.

## 보유 차량과 근무 차량의 차이

- 마지막 30분: 합계가 80 미만 · 대기 승객 증가
- 원인: 차량별 work_start · work_end
- 자정 근접 → 근무 중 차량 감소
- 결과 해석 시 구분: 전체 차량과 현재 근무 중인 차량

> fleet_size가 80이어도 모든 차량이 전 시간대에 근무하는 것은 아닙니다. 결과를 해석할 때는 전체 차량 수와 해당 시각의 근무 차량 수를 구분해야 합니다.
