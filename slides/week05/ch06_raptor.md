# 교재 6.1 라운드 기반 탐색

## 시각-정류장 그래프의 한계

- 대안: 정류장과 시각의 쌍을 노드로 구성
- 규모: 시각표 행 65만 개가 그대로 노드 수
- 추가 문제: 출발 시각이 바뀔 때마다 재구성 필요
- RAPTOR의 관점: 환승 횟수를 라운드로 사용

> 억지로 그래프를 만들 수는 있지만 크기와 재구성 비용에서 실패한다.

## 라운드의 정의

- 라운드 0: 도보로 도달 가능한 정류장
- 라운드 1: 한 번 탑승해 도달 가능한 정류장
- 라운드 k: k번 탑승해 도달 가능한 정류장
- 종료 조건: 환승은 대개 네다섯 번을 넘지 않음

> 라운드마다 새로 도달한 정류장을 보관하고 그 정류장을 지나는 노선만 순회한다. 우선순위 큐도 정렬도 없이 순서대로 순회하기만 한다. 이 단순함이 RAPTOR가 빠른 이유다.

# 교재 6.2–6.4 세 가지 준비

## 노선이 아니라 패턴

표: 하남 GTFS의 노선, 운행, 패턴 규모
| 단위 | 개수 | 뜻 |
|---|---|---|
| 노선 | 169개 | GTFS의 route_id |
| 운행 | 8,923개 | 개별 차량의 1회 운행 |
| 패턴 | 349개 | 정류장 순서가 완전히 같은 운행의 집합 |

- route_id를 그대로 쓸 수 없는 이유: 상하행 순서 반대, 지선 분기
- 패턴당 평균 26회 운행
- 패턴 내 운행은 첫 정류장 출발 시각 순으로 정렬 — 이분 탐색 대비

> 노선당 패턴 수는 96개 노선이 1개, 61개가 2개(상하행), 나머지 12개가 4개에서 22개다. 패턴이 22개인 노선은 지선이 여럿이거나 시간대별로 일부 구간을 생략하거나 회차 지점이 여러 개다.

## 정류장에서 패턴으로의 역색인

- 필요: 라운드마다 이 정류장을 지나는 패턴 조회
- 매번 349개 패턴을 순회하면 느림 — 사전에 역방향 색인 구성
- 저장 내용: 패턴 번호와 그 패턴에서의 정류장 위치
- 위치가 필요한 이유: 해당 지점부터 순회해야 함

> 가장 많은 패턴이 지나는 정류장이 어디인지 교재에서 함께 확인한다.

## 도보 환승 생성

- 한국 GTFS에는 transfers 파일이 대부분 없음 — 직접 생성
- 생성 규칙: 500 m 이내 정류장 쌍
  - 직선거리에 1.35를 곱해 우회 반영
  - 초속 1.2 m로 나눠 도보 시간 산출
- 결과: 도보 환승 28,818쌍 · 정류장당 평균 7개
- 평균이 큰 이유: 버스 정류장이 도로 양쪽에 하나씩 존재

> 직선거리 기반 값은 낙관적이다. 한강을 사이에 둔 두 정류장이 직선 400 m면 환승이 생성되지만 실제로는 다리를 건너야 한다. 실제 엔진은 보행 네트워크에서 다익스트라로 이런 쌍을 제외한다.

# 교재 6.5 알고리즘

## 상태와 라운드 0

- best[정류장] — 현재까지 알아낸 가장 이른 도착 시각
- rounds[k][정류장] — k회 탑승으로 도달했을 때의 도착 시각
- marked — 직전 라운드에서 개선된 정류장 집합
- 라운드 0: 출발지에서 도보로 닿는 정류장에 출발 시각 + 도보 시간 기록

> 상태 세 개만 이해하면 나머지는 반복문이다. 교재에서 raptor_core를 한 줄씩 함께 확인한다.

## 라운드 k의 네 단계

- 1단계: 표시된 정류장이 속한 패턴 수집 — 가장 앞 위치부터 시작
- 2단계: 각 패턴을 그 위치부터 끝까지 순회
  - 탑승 중이면 하차 시각 갱신 시도
  - 더 이른 운행이 있으면 그 운행으로 변경
- 3단계: 이번 라운드 도달 정류장에서 도보 환승 반영
- 4단계: 개선된 정류장이 없으면 종료

> 새로운 부분은 2단계다. 패턴을 한 번 순회하면서 탑승 상태를 유지하고 더 이른 운행이 있으면 교체한다.

# 교재 6.6 경로 복원과 지표

## 실행 결과

표: 하남시청 출발 오전 8시 RAPTOR 실행 결과
| 항목 | 값 |
|---|---|
| 실행 시간 | 80 ms |
| 도달 정류장 | 4,156개 |
| 전체 정류장 | 4,203개 |

- 한 번 실행으로 모든 정류장의 도착 시각 산출 — 일대다 결과
- 다익스트라로 한 쌍씩 4,156회 질의하는 것보다 빠름
- 접근성 지도를 그릴 때 이 성질을 그대로 사용

> 라운드마다 이 정류장에 어떻게 도달했는지 기록해 두면 역방향으로 경로를 복원할 수 있다. 정리된 구현이 그렇게 되어 있다.

## 이동하지 않는 시간이 더 김

표: 하남시청에서 미사역까지 오전 8시 출발 통행시간 내역
| 구분 | 시간 |
|---|---|
| 차내 | 6.6분 |
| 도보 | 11.2분 |
| 대기 | 5.1분 |
| 합계 | 약 23분 |

- 같은 구간 승용차 오전 첨두 소요시간은 약 8분
- 대중교통이 세 배 가까이 소요
- 개선 방향: 배차간격 단축과 정류장 접근성

> 이동 시간보다 이동하지 않는 시간이 길다. 대중교통 개선이 배차간격과 접근성에 집중되는 이유이고, 기말 프로젝트 시나리오 선택의 근거가 된다.

# 교재 6.7 검증과 정리

## 작은 시간표와 불변식

- 실제 GTFS로는 정답을 손으로 확인 불가 — 답을 아는 소형 시간표 사용
  - 직통 도착, 환승 1회 도착, 출발 5분 지연 시 다음 차 탑승
- 실제 피드에서는 불변식 확인
  - 30분 늦게 출발했는데 더 일찍 도착한 정류장이 0개
  - 새벽 3시 출발 시 도보로 닿는 정류장만 도달

> 늦게 출발했는데 더 일찍 도착하는 일은 있을 수 없다. 하나라도 나오면 구현이 틀린 것이다. 검증 코드는 tests/test_raptor.py에 있다.

## 오늘의 정리

- 대중교통은 도착 시각에 따라 비용이 변동 — 그래프 최단경로 사용 불가
- RAPTOR는 환승 횟수를 라운드로 사용, 우선순위 큐와 정렬이 없음
- 운행 8,923개를 패턴 349개로 통합해 정류장 순서를 확정
- 1회 실행에 80 ms, 정류장 4,156개의 도착 시각 산출

> 하남시청에서 미사역까지 오전 8시는 23분이고 그중 차내가 6.6분이다. 이 수치가 7장 지표와 기말 프로젝트로 이어진다.
